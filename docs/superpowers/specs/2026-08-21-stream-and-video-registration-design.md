# 监控推流性能与视频人脸注册设计

## 目标与边界

本次工作由两个独立模块组成，按顺序实施、独立验证：

1. 优化监控预览推流，使局域网浏览器中的画面更流畅、延迟不随慢客户端累积。
2. 增加“本地正脸视频注册”功能，同时将前端视频帧来源抽象为可扩展接口，以便以后接入浏览器摄像头录制。

不更换 InsightFace 模型包，不改动现有人脸 embedding，不删除人脸库或事件记录。视频注册不保存整段原始视频，服务端仅在请求生命周期内处理前端抽取的 JPEG 帧。

## 已验证的性能事实

在 `D:\test6.mp4`、`cam-0`、RTX 4060 Laptop GPU 上测得：

- 推理主循环稳定在 60 FPS 上限；检测阶段滚动均值约 11.4 ms，因此推理不是当前主要瓶颈。
- WebSocket 客户端实际接收约 13 FPS；当前配置的 `push_fps` 上限为 15 FPS。
- `cam-0` 的数据库配置将 `stream.max_height` 覆盖为 `0`，导致浏览器接收 1280×960 原图。
- 当前协议是“JPEG → Base64 → JSON 文本 → WebSocket”，并在前端逐帧 JSON 解析、Data URI 解码、JPEG 解码、Canvas 重设尺寸和绘制。
- 同一视频的 JPEG 基准：960px 高约 3.31 ms / 95 KB Base64；480px 高约 0.95 ms / 37 KB Base64。不同画面内容下，实测 Base64 帧可达约 207 KB。

结论：优先优化预览图分辨率、二进制传输、慢客户端背压和前端解码渲染；不要以降低识别阈值或更换模型来解决卡顿。

## 模块一：监控推流性能设计

### 传输协议

后端与前端同时升级到 `binary_jpeg_v1`：

- 视频帧使用 WebSocket 二进制消息，不再把 JPEG 转成 Base64 或包入 JSON。
- 二进制包格式固定为：`1 byte message_type (0x01) + 8 bytes big-endian frame_id + JPEG bytes`。
- 检测框仍使用小型 JSON 文本消息：`{ type: "detections", frame_id, persons }`。
- 前端仅在显示指定 `frame_id` 时使用对应帧号的检测结果；没有对应结果时显示视频，不绘制旧框到新画面上。

### 后端背压与指标

保留“每摄像头一个 JPEG 编码线程 + 单槽位编码队列”的现有设计，并增加“每订阅者一个单槽位发送队列”：

- 编码线程只生成最新 JPEG；满队列时丢弃旧帧。
- 每个 WebSocket 客户端拥有独立发送 worker；慢客户端只替换其待发送旧帧，不能阻塞其他客户端，也不能在事件循环中积压发送协程。
- 客户端断开时取消其 worker，释放队列和引用。
- 发送过程不得持有全局锁。
- 指标增加：`preview_enqueue_fps`、`encoded_fps`、`sent_fps`、`encode_dropped_frames`、`subscriber_dropped_frames`、`avg_jpeg_bytes`，并保留现有采集/检测/任务阶段耗时。

### 分辨率、帧率与前端渲染

- 默认预览高度保持 480px；设置页面应向用户说明 720px 是清晰度与流畅度的折中，1080px/原生适合仅在网络与设备足够时使用。
- 不静默覆盖数据库中已有的 `stream.max_height: 0`。现有摄像头由用户在设置页手动改为 480 或 720；新摄像头默认继承 480。
- 初始 `push_fps` 设为 20，并允许配置回退到 15；只有在二进制协议、480/720p、局域网实测通过后才允许提升到 25。
- 前端以 `Blob` 和 `createImageBitmap()` 解码 JPEG，通过 `requestAnimationFrame` 绘制最新一帧；新的未绘制帧覆盖旧的待绘制帧，始终优先低延迟。
- Canvas 只在画面实际尺寸变化时设置 `width` 和 `height`；每个 `ImageBitmap` 绘制后必须 `close()`，避免内存泄漏。

### 验收标准

- 在 `D:\test6.mp4` 上，480/720p 预览的本地实际显示帧率达到配置帧率的 90% 以上（20 FPS 配置时至少 18 FPS）。
- 慢 WebSocket 客户端不会降低其他订阅者的发送速率，也不会无限增加端到端延迟。
- 无订阅者时不进行 JPEG 编码；推理吞吐不因预览优化下降。
- 现有抓拍、检测框、事件 WebSocket 和摄像头启停功能保持可用。

## 模块二：本地正脸视频注册设计

### 用户体验

在人脸库中新增“视频注册”入口，打开四步弹窗：

1. 选择身份模式：注册新人，或给现有人脸补充特征。
2. 上传本地视频文件并播放预览；展示时长、抽帧进度和取消按钮。
3. 自动分析候选帧后，展示 5～8 张推荐正脸缩略图、时间点、质量原因与人脸框；用户可删除任意候选帧。
4. 确认提交。新身份填写姓名和备注；补充身份选择已有身份。成功后刷新人脸库和 embedding 数量。

第一版只实现本地文件上传，不调用 `getUserMedia`，不保存原视频。未来的摄像头注册使用相同页面状态与后端接口，只替换帧来源。

### 前端帧来源抽象

定义与 UI 无关的接口：

```ts
interface VideoRegistrationSource {
  open(): Promise<void>;
  getDuration(): number;
  extractFrame(timestampMs: number): Promise<Blob>;
  close(): void;
}
```

- `UploadedVideoSource`：第一版实现。基于 `HTMLVideoElement`、受控 seek 和 Canvas，从用户选择的文件提取 JPEG 帧。
- `CameraVideoSource`：仅定义未来实现位置，不在本次调用摄像头。它将输出同样的 `Blob`，因此不会改动候选分析或提交接口。

客户端限制：默认最大时长 60 秒、最大文件 100 MB；采样间隔 500 ms；前端最长抽取 120 帧。超出限制须在开始前明确提示，不能让浏览器或后端无界处理大文件。

### 后端 API 与服务边界

新增两个专用接口，图片注册接口保持兼容：

- `POST /faces/video-registration/analyze`：接收一批候选 JPEG 帧和对应的 `frame_id`、`timestamp_ms`，只返回分析结果，不写数据库。
- `POST /faces/video-registration/commit`：接收用户最终选定的 3～8 张 JPEG 帧，以及 `mode=create|append`、新身份的姓名/备注或现有 `identity_id`。服务端再次执行质量校验，成功后原子地创建身份或追加 embedding，并刷新内存 gallery。

后端服务层必须抽出可复用的“批量 embedding 提取和入库”方法。普通图片批量注册与视频注册应共享质量校验和入库逻辑，避免两套规则漂移。

提交的 embedding `source` 记录为 `video`；不引入原始视频表或临时文件持久化。分析接口与提交接口都要限制图片数量与总请求体大小。

### 候选帧质量规则

每张候选帧在后端依次执行：

1. 必须只检测到一张人脸；多人、无人脸帧拒绝。
2. 使用现有注册质量门槛：检测置信度和人脸最短边。
3. 使用 InsightFace 关键点判断是否为近似正脸；偏航、俯仰或关键点异常的帧拒绝或降分。
4. 在人脸区域计算轻量清晰度分数；阈值放入配置，不能硬编码。
5. 提取归一化 embedding；与已入选候选帧比较余弦相似度，过于相似的连续帧去重。
6. 按质量分和时间分布选出目标数量的候选帧，避免全部来自视频同一秒。

分析结果必须包含每帧的接受/拒绝状态、拒绝原因、质量分、时间点、检测框和用于前端预览的 `frame_id`。用户手动删除后，服务端提交时仍必须复验；不得信任前端传来的质量结论。

默认需要至少 3 张合格且非重复的帧，最多提交 8 张。无法达到最低数量时不创建/修改底库，并明确展示拒绝原因。

### 失败处理与安全规则

- 读取视频、seek 失败、浏览器不支持视频编码、后端检测失败，都必须停止进度并显示可操作的提示。
- 用户取消、关闭弹窗或重新选择文件时，释放 Object URL、Canvas 与待处理请求；已产生但未提交的候选帧不得入库。
- 提交途中失败时，后端不得留下半创建身份或部分 embedding；使用事务保证 create/append 的原子性。
- 视频中出现多个人时，默认整帧拒绝，不自动猜测谁是目标人员。
- 不改变现有图片注册和图片识别接口的响应格式。

## 编码流程与硬性规定

### 实施顺序

1. 为推流协议与发送队列补充失败测试和运行指标，再实现二进制传输与前端解码。
2. 在本地视频上完成 480/720p、15/20 FPS 的测量，选择默认值；不将未经实测的参数写死。
3. 编写视频注册纯函数测试：抽帧计划、候选去重、质量排序、最少帧数规则。
4. 实现后端分析/提交服务和 API，先用接口测试验证不写库分析、事务提交和 append/create 两种模式。
5. 实现 `UploadedVideoSource` 与视频注册弹窗，接通推荐帧确认和提交。
6. 使用真实本地正脸视频做手工验收；确认后只预留 `CameraVideoSource` 接口，不实现实时摄像头录制。

### 不可违反的规则

- 每一步只解决一个模块，不把性能优化、人脸识别阈值和视频注册逻辑混在同一改动中。
- 先写测试或最小可复现指标，再实现；没有测量不能宣称“更流畅”或“更准确”。
- 不引入新的模型、超分辨率、FFmpeg 服务端依赖或数据库大迁移。
- 不发送 Base64 图像作为新推流协议；不在 WebSocket 事件循环中做 JPEG 编码。
- 不保存整段视频、不自动清空或重建人脸库、不因视频注册降低已有注册质量门槛。
- 所有可调阈值、时间、帧数、文件大小和分辨率均进入配置，不在业务逻辑中硬编码。
- 保持工作区中现有的未提交“识别稳定性”改动原样；本任务不得覆盖或回退它们。
